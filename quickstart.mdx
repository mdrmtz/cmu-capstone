**The A11y Fixer** automates WCAG 2.2 AA remediation in Angular codebases. It takes an `axe-core` audit report as input and delivers a verified, regression-free Pull Request as output — no manual code editing required.

## How it works in three steps

<Steps>
  <Step title="Audit — detect violations">
    The A11y Fixer runs a real `axe-core` audit itself — point it at a repo or a live URL and it builds the structured JSON violation report internally, no separate manual audit step required. Each record captures the failing DOM node, its CSS selector, and the specific WCAG criterion it violates.

    ```bash
   source agent/.venv/bin/activate && python -m a11y_fixer.cli audit --config agent/sites.yaml
    # or, against an already-running site:
   source agent/.venv/bin/activate && python -m a11y_fixer.cli fleet --config agent/sites.yaml
    ```
  </Step>
  <Step title="Retrieve — fetch authoritative context">
    The **Compliance Planner Agent** resolves every violation with a **live `wcag-mcp` call** — never from static training data. Given the rule id, selector, and failing DOM node, it queries `wcag-mcp`'s 20 tools for the matching WCAG success criterion, sufficient/advisory techniques, and known failure patterns, then validates the candidate against framework-specific anti-patterns.

    A separate, file-backed memory loop feeds past HITL rejections back in: every "reject + constraint" decision is appended to `wiki/AGENTS.md`, loaded as static context on every run, so the agent never repeats a fix a human already rejected for the same reason.
  </Step>
  <Step title="Remediate — patch, verify, and deliver">
    The **Codebase Compiler Agent** locates the exact component file deterministically (selector + hint-text matching, not an LLM guess), applies a minimal patch, and hands it to **`RubricMiddleware`** — a grader loop (max 3 iterations) that re-scores and requests a revision until the rubric is satisfied or iterations run out. Each candidate is scored by the **QA Critic Agent** on a 0–20 rubric:

    | Metric | Weight |
    |---|---|
    | Angular Ivy compile safety | 8 pts |
    | AST structural validity | 4 pts |
    | WCAG semantic compliance | 5 pts |
    | Visual layout stability (≤2% shift) | 3 pts |

    Patches scoring ≥15/20 (P(IK) ≥ 0.75) may route to "auto"; ≥18/20 auto-merges immediately. Everything else — lower scores, high-risk rules, or the model's own uncertainty — lands in a persisted `hitl_queue/` ticket for human review via the Bounded Decider dashboard. A full Tree-of-Thought DFS search (`domain/tot_search.py`, k=3 siblings with adaptive inflation to k=5) is real, tested code, but today it scores the **offline evaluation harness's** benchmark, not this live remediation loop.
  </Step>
</Steps>

## Key concepts

| Term | Meaning |
|---|---|
| `axe-core` | Open-source accessibility auditing engine — produces the violation report the agent consumes |
| `wcag-mcp` | Live WCAG 2.2 knowledge server — sole source of truth for success criteria/techniques, queried fresh on every violation, never cached |
| RubricMiddleware | The live grader loop (max 3 iterations) that re-scores and requests revisions on the Codebase Compiler's single working candidate |
| Tree-of-Thought (ToT) | `domain/tot_search.py` — a real, unit-tested k=3-sibling DFS search, wired into the **offline evaluation harness only**, not the live agent |
| Angular Ivy compiler | The compilation target used to validate every patch before scoring |
| Git reset between violations | `_capture_and_reset_git_changes()` diffs the fixture against `HEAD`, then runs `git checkout -- .` + `git clean -fd` so each violation starts from a clean baseline |
